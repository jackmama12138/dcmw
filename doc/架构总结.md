# DCMW 架构总结

## 整体架构

```
[Client]
  POST /task/add
       │
       ▼
[Gateway]  :7777
  Express  → HTTP API + 静态 UI
  ws.Server → /ws/livetop  (Worker 通信)
  Scheduler → 任务分配逻辑
  Redis     → 任务状态持久化
       │
       │  原生 WebSocket
       │
[Worker × N 台机器]
  ws.Client → 一个连接到 Gateway
  ChromePool → 内部管理 N 个 Profile
  Playwright → 执行 pipeline
```

## 目录结构

```
dcmw/
  gateway/
    src/
      index.js          进程入口，组装所有模块
      config.js         环境变量读取与验证
      logger.js         Winston 日志（按天存储，7天自动清理）
      redis.js          ioredis 客户端（自动重连）
      task-store.js     任务的 Redis CRUD + 状态计算
      worker-registry.js  内存中的 Worker WS 连接 + slot 状态
      scheduler.js      将 pending 任务分配到 idle slot
      ws-server.js      WebSocket 升级处理 + 消息路由
      router.js         Express 路由（任务提交 + 状态 API）
    public/
      index.html        Dashboard（纯原生 JS，轮询刷新）
    .env
    package.json

  worker/
    src/
      index.js          进程入口，env 校验、生命周期管理
      logger.js         Winston 日志（同上）
      chrome-pool.js    Chrome Profile 实例池（idle/busy/error 状态机）
      task-runner.js    执行 pipeline，exactly-once 回调
      ws-client.js      原生 ws 客户端，指数退避重连，30s 心跳
      actions.js        navigate / wait / click / scroll / close
    .env（共用根目录 .env）
    package.json
```

## WebSocket 消息协议

所有消息格式：`JSON`，字段 `type` 标识类型。

### Worker → Gateway

| type | 字段 | 说明 |
|------|------|------|
| `register` | `worker_id`, `profiles[]`, `slots` | Worker 上线注册 |
| `heartbeat` | `worker_id`, `slots` | 30s 心跳 |
| `task_result` | `task_id`, `profile`, `status`, `target_url`, `error?` | 任务执行结果 |
| `task_rejected` | `task_id`, `profile`, `reason` | 拒绝执行（slot 非空闲） |
| `pong` | — | 回应 ping |

### Gateway → Worker

| type | 字段 | 说明 |
|------|------|------|
| `task` | `task_id`, `profile`, `target_url`, `pipeline[]`, `task_time` | 分配任务 |
| `ping` | — | 保活检测 |

## HTTP API

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/task/add` | 提交任务 |
| `GET` | `/api/tasks` | 查询任务列表（最近 100 条） |
| `GET` | `/api/tasks/:id` | 查询单个任务 |
| `GET` | `/api/workers` | 查询 Worker 状态 |
| `GET` | `/` | Dashboard 页面 |

## 任务状态机

```
pending → running → done
           ↑  ↓
         （部分 slot 完成后继续分配）
```

任务字段：

| 字段 | 说明 |
|------|------|
| `count` | 需要执行的总实例数 |
| `running` | 当前正在执行的实例数 |
| `completed` | 成功完成数 |
| `failed` | 失败/超时数 |
| `status` | `pending / running / done` |

调度逻辑：每当有 slot 释放（task_result / register），Scheduler 触发一次 dispatch，将 `count - running - completed - failed` 个实例分配给 idle slot。

---

## 关键防御性设计

- **ChromePool 状态机**：acquire 前校验 state === idle；浏览器意外断连自动标为 error
- **task-runner settled 标志**：timeout 和 error 共用 `settle()`，onComplete 只触发一次
- **Gateway 重启恢复**：启动时 `resetRunning()` 将所有 in-flight 任务重置为 pending，重新调度
- **Scheduler 并发保护**：`_dispatching` 标志防止重入，事件触发的多次 dispatch 折叠为一次
- **WS 重连**：指数退避（3s → 6s → 12s → ... → 30s 上限）
- **进程级防护**：`uncaughtException` + `unhandledRejection` 均写入日志，不静默崩溃
